## Type And Adapter Policy

The goal is not to make every mathematical combination executable. The goal is to make every coherent route resolvable and every incoherent route explainable.

Required invariants:

- Direct type identity is preferred.
- Safe non-lossy adapters may resolve automatically.
- `visible_default` adapters may resolve only where the declared UI projection already exposes that semantic choice.
- `explicit_only` adapters require persisted explicit consent and must appear in graph/application receipts.
- Lossy normalization must never be silently inserted.
- Category, phase, scalar, color, mask, and raw field domains remain distinct.
- Known-invalid examples remain fail-closed: root category into scalar repeat, phase into a root-category palette, and raw SDF field into a phase palette.
- Resolver diagnostics identify the blocking edge, source and destination types, candidate adapters, required consent, and final reason.

## Composite Function V1 Follow-Up Specification

Composite functions are the leading next campaign after the mandatory stop/replan. They are documented now but are not authorized for runtime implementation under this campaign.

### Semantic Boundary

- A recipe selects/configures a complete pipeline.
- A composite function is an embeddable, parameterized typed subgraph with one or more typed inputs and outputs.
- A composite may project into the current linear row editor, but the wrapper identity and internal graph remain reviewable authority.

### Required Contract

`viewer.composite_function_contract.v1` should include:

- stable composite ID, version, canonical content hash, label, and classification;
- typed input/output ports and producer capability requirements;
- explicit semantic internal node IDs and typed edges;
- approved adapter identities and consent policy;
- exposed parameter descriptors;
- deterministic mappings from exposed parameters to internal descriptor parameters;
- namespaced expansion IDs;
- fail-closed reasons;
- canonical expansion fingerprint;
- state, report, capture, and replay behavior.

Parameter plumbing may use only a small pure declarative mapping surface such as identity, scale, offset, clamp, invert, and smoothstep. Arbitrary C++ callbacks are forbidden. A named/versioned runtime operation requires its own contract and proof.

### Materialization And Receipts

- Resolve and validate the complete composite before authoritative mutation.
- Expand into current runtime rows initially; do not require visible graph UI.
- Preserve both wrapper identity and expanded node/edge/parameter receipts.
- Stable namespaced IDs must survive internal insertion/reordering when semantic IDs do not change.
- A prepared composite commit must be non-failing and transactional under the existing recipe application boundary.

### Candidate First Modules

- `signed_relief_v1`: signed scalar through normalization/window, diverging palette, and contrast grading.
- `phase_ribbons_v1`: phase offset/repeat/mirror through cyclic palette and finish.
- `distance_contours_v1`: signed distance through contour shaping and palette.
- `boundary_glow_v1`: scalar or mask input through glow materialization.
- `categorical_two_tone_v1`: category input through two-tone color and finish.
- `root_glow_material_v1`: reusable root-distance material separated from the full Root Glow recipe.

### Composite V1 Gates

- Shadow materialization parity first.
- One lane-local composite before a cross-lane composite.
- One live pilot only after deterministic expansion and receipt proof.
- Existing linear UI remains a projection; graph UI stays deferred.
- No Salticid runtime dependency; UI-Salt/materialized JSON remains the authoring boundary.
